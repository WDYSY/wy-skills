# 手写体文档

骨架按金字塔原理搭，血肉按人记笔记的口吻填。金字塔管"先说什么、每段凭什么存在"，口吻管"怎么说才不像机器"，块版面只在真能帮读者看懂或核对时才上。冲突时以前者为准。

## 一、最高准则：金字塔原理

一篇给别人看的文档，只有一棵金字塔。下面四条是硬约束，违反任何一条，其余写得再好也没用。

### 1. 结论先行

第一屏给答案。读者只看开头一段，就该知道这篇在说什么、他该做什么决定。

- 结论是**判断句**，有主语、有态度：写"评分只能用来缩候选，不能直接定选型"，不写"关于模型评分的若干思考"。
- 结论要能被反驳。反驳不了的话是废话，不是结论。
- 需要突出的放一个 `<callout>`；不需要就用段落第一句写。**不是每节都要有个框。**

### 2. 纵向问答

上一层的每句话，都要在下一层引出问题；下一层的每一组，都要回答那个问题。一层层降下去，直到读者不再问"凭什么"。

- 自检话术：读一句结论，紧接着问"凭什么"。下一块不是答案，就是断链。
- 断链比缺失更糟：中间插一段和论证无关的内容，读者会以为你在转移话题。

### 3. 横向 MECE

同一层的几个点，必须是同一类东西，彼此不重叠，合起来答完，不多不少。

- 分组要能起带数字的概括句：「三个原因导致 X」「四条硬规则」「两种取数方式」。写不出数量，通常是没分好组。
- 只有一条的"分组"不成立——那就别用列表，写成一句话。
- 超过七条，往上再分一层。

### 4. 顺序只有三种

因果演绎、时间顺序、结构顺序，外加重要性降序。同一组里只能选一种，混着排读者就迷路。

- 讲过程用时间序，讲系统组成用结构序，讲结论和建议用重要性序。
- 演绎链超过两步读者会跟丢，改成归纳 + 分组。

### 序言用 SCQA，但别写出这四个字

情境 → 冲突 → 疑问 → 回答，三句话连成一段递进就够。写成"背景：""冲突："这种标签，立刻变 AI。

### 和手写口吻冲突时怎么裁

- 手写体允许碎片、口语、保留意见，**但这些只能长在枝叶上，不许破坏主干**。
- 确实没结论的（第一轮调研、边查边记）：第一屏直接写"这是过程记录，结论未定"，并列出哪几条已经确定。此时金字塔降级为"每节内部结论先行"。
- 空小节、待补、存疑、存档一律放到主体之后（「其他」），不许插在论证链中间。
- 归档段是附录，可以不符合金字塔，也不参与正文逻辑。

细化方法（三条基本规则、归纳与演绎之别、SCQA 的写法、三种典型反模式、三组改写示例）见 `references/pyramid.md`。

## 二、生成前先确认 content

**没确认内容就不落盘。** 出 brief 之前先搜内部资料，别只拿外网网页当依据。

brief 自己也要金字塔化：先说结论，再给支撑，最后给待定。

1. 一句话结论：这篇要证明什么、让读者做什么。
2. 一级支撑：3-5 条，每条一句判断（这就是将来的 h2）。
3. 每根支撑下面的证据：关键数字、要引的文档（token 或链接）、原始材料。
4. 落点：放哪个 wiki / 云空间，标题叫什么。
5. 我不确定的点：需要用户拍板的，逐条列出。

用户回「可以 / 按这个来」之后才写。改内容要重新确认；只改措辞和排版不用。

例外：用户已经把内容和结构给全了（贴了完整正文、或明确说"就按这个大纲写"），直接写，但要说明"按你给的结构直接写，没有再确认"。

搜内部资料：

```bash
lark-cli docs +search --query "<主题 关键词>" --as user \
  --jq '.data.results[] | [(.result_meta.token // ""), (.result_meta.doc_types // ""), (.title_highlighted // "")] | @tsv' --json
```

换三四个关键词各搜一遍，命中的先看 outline 再决定引不引。内部文档 chip 比外网链接硬——外网是别人说的，内部是我们自己做过的决定。搜索走 LarkCli 工具，shell 里的 lark-cli 会报 not_configured。

## 三、骨架

一级章节用流程词导航，二级以下标题写判断。这是金字塔在长文档里的落地方式：h2 说"这部分讲什么"，h3 说"这部分得出什么"。

### 文档标题写交付物，不写问句

- 格式：`<体裁>：<对象> 的 <产出物>`。例：`调研：vai 与 B 端流程的指令对齐方案`。
- 体裁前缀就用这五个：调研、方案、复盘、纪要、手册。
- 产出物后缀决定读者预期：方案＝给出了做法，结论＝给了判断，手册＝能照着查，复盘＝讲清了为什么。
- **问句一律不行**：`指令怎么对齐`、`如何落地`、`是否可行`、`为什么慢`——这是选题，不是交付物。读者看到问句，不知道点开能拿到什么。
- 标题和节标题分工不同：标题标交付物（名词），节标题写判断（句子）。别把结论塞进标题，也别把问句塞进节标题。

```xml
<title>调研：vai 与 B 端流程的指令对齐方案</title>
<h2>一、背景</h2>
<h2>二、调研</h2>
<h3>三个综合榜的口径互不兼容</h3>
<h3>单项基准更适合选型</h3>
<h2>三、结论</h2>
<h2>其他</h2>
<h3>存疑</h3>
<h3>会议纪要</h3>
<h3>存档</h3>
```

- 一级：背景、调研、结论、其他这种 2-4 字流程词，只负责导航。
- 二级及以下：写判断，4-14 字。"单榜第一不等于全局第一"行，"几个观察"不行。
- 二级标题禁用标签词：说明、介绍、概况、相关、情况、详情、内容、概述。出现这些词，说明这节还没想清楚要证明什么。
- 层级不必补齐。`<h2>` 下面直接 `<h4>` 也行，人不会为了对称补一级。
- 归档自成体系：写完不删，挪到「存档」下，标题写清结论，保留当时的前提、被否决的路线（删除线）、产物链接、以及为什么停了。不再跟进的单独一节「暂不再跟进」。

## 四、块版面：工具箱，不是检查表

默认输出 XML，不要输出 markdown。下面这些块在真能帮读者看懂或核对时才用。

| 信息 | 块 | 什么时候值得用 |
|---|---|---|
| 全篇结论、风险 | `<callout>` 或 `<blockquote>` | 一句话要跳出正文才不被扫过去 |
| 关键术语、指标名 | `<span text-color>` | 同一段里有并列的专有名词 |
| 命令、配置、接口返回 | `<pre lang caption><code>` | 内容本身就是代码或原始报文 |
| 跨文档依据 | `<cite type="doc" doc-id>` | 有别的文档能证明这句 |
| 原始数据、录屏、原文件 | `<source>` | 读者可能想自己复算 |
| 真对比、before/after | `<grid>` 两列 | 两份东西要左右对着看 |
| 待办、检查项 | `<checkbox done>` | 这件事有明确的下一步 |
| 口径表、字段说明 | `<table>` + `<colgroup>` | 有行列关系，改成段落会更长 |
| 截图说明 | `<img caption>` | 图本身需要一句话解释 |

### 用不上就别用

- 这些东西是备选，不是清单。一篇里没有表格、没有彩色词、没有引用块，都是正常的。
- 判断标准只有一条：加了它，读者是不是更快看懂或更容易核对。只是为了"丰富一点"，别加。
- 几条红线：三行以内的内容不用表格；一句话的结论不用框，段落首句就够；不是并排对比就别用 grid；没有跨文档依据就别挂 chip；彩色词全篇超过五个就删到五个。
- 宁可整篇只有段落、一张表和一个代码块，也不要每节都塞一个高亮框。**堆满块比全是段落更假。**

### 关于"全是段落"

连着三段都是普通段落时，先看是不是该合并、该补数据、该拆句。如果内容本身就需要这样铺陈（讲一段过程、讲一段背景），保持原样。不要为了让版面看着丰富去硬拆硬插。

颜色只染名词，不染整句，同一语义前后同色。

完整 XML 写法与坑见 `references/feishu-blocks.md`。

### 表格：每一格都要能核

表格最容易写成 AI 味，因为默认写法是每格一句解释。判据只有一条：把表给一个没读正文的人，他能不能**点开、复算、对数字**。不能就是没写完。

- 列不许叫「说明」「备注」「简介」。这类列一出现，内容必然是空话。
- 第一列是标识：文件名、榜单名、字段名，套 `<code>`。
- 最后一列放**能点或能复算**的东西：链接、取数路径、csv 附件、chip。
- 中间放判断依据，写成"数字 + 口径"，不写句子。行数、分数、占比、条数、更新时间，能数就数。
- 表上方一行写来源和取数时间；表下方给一段能跑的命令。
- 单元格里可以放链接、行内代码、chip、勾选框、多层列表。该用的时候别只写一句解释。
- 列数 3-5。超过 5 列说明在排版，不是记账。

**例外**：字典型表格（字段 → 含义 → 取值）本来就是给人查的，纯文字就是正确答案，别硬塞链接和数字。判断标准回到那条：这张表是给人**核对数据**还是给人**查词**，前者要证据，后者要清楚。

反例（只有判断，没有证据）：

```xml
<tr><td>best-100</td><td>综合"值不值得装"，五个维度加权成一个分</td><td>首次出现满 30 天的技能</td></tr>
```

正例（同一行，加了数据、代码、链接）：

```xml
<tr>
  <td><code>best-100</code></td>
  <td>综合"值不值得装"</td>
  <td>首次出现满 30 天</td>
  <td>100 行；skills.sh 88 / clawhub 12；#1 <span text-color="green">agent-browser</span>，wis <b>77.5</b></td>
  <td><a href="https://…/rankings/best-100.csv">rankings/best-100.csv</a></td>
</tr>
```

## 五、证据链：结论 → 数据 → 出处

金字塔的每根柱子底下都要有东西撑着，否则整棵树是空中楼阁。

1. 观察：一句话，能被反驳。例：HLE 榜前十有三个国产模型，综合榜一个都没有。
2. 数据：带量级、单位、口径、时间。例：Kimi K3.1 Pro 70.00 第一，DeepSeek-V4.1-Flash 63.90 第六，页面版本 10-29。
3. 出处：`<cite>` chip、裸 URL、附件 chip、或一段原始返回。**内部文档优先于外网链接。**

- 数字必须能被复算。写"约 33.7 秒"不写"很快"；写"51 次 HTTP 请求"不写"请求很多"。
- 对比给两边的数。"V2 0.2 秒 vs V1 14.3～44.7 秒"，不写"明显更快"。
- 结论后面紧跟证据，别堆到文末"参考资料"。看一句能验一句。
- 重要的地方挖四层：结论 → 子结论 → 数字 → 原始报文。次要的一句话带过。**深度不对称才是人写的**，每节一样深是 AI。
- 现场要留：抓取时间、页面版本、接口 revision、第几次尝试、失败的尝试。
- 存疑单列一节：没验证的、抓不到的、口径没写清的。这一节最像人。
- 外部和内部对上了就写出来。外部榜单说这是第一梯队、内部通知说这型号被封禁，两句摆一起比任何分析都硬。
- 不是每个结论都能找到数据。找不到就降级写"这条没验证"，比编一个数字强。

## 六、怎么写句子

- 一段一句。写长了自己都读不下去，拆开。
- 动词具体：跑通、兜底、回退、蒸馏、挪、捞、贴、卡住、抖动。少用实现、完成、构建、落地。
- 数字带口径和不确定词：约 33.7 秒、51 次 HTTP 请求、14.3～44.7 秒、出现过一次 15 秒冷启动。
- 方括号标状态：【最终采用】【7-30 官方社区提供】。日期写 7-30、8-11。
- 中英混写不套壳：V2 MCP 直连、agentark_client.py、AGENTARK_TOKEN 直接写。
- 该保留意见就保留：不靠谱的直接写"这条是拿组名字面猜的，不够可靠"。
- 否决过的方案用删除线留着，别删干净。

**行内代码可以用，但要少**。用在三种地方：要强调的词、数据口径和指标名、真代码和命令，比如 `recall@5`、`top_k`、`prd_meid`。每 20 行不超过 3 处，同一列表里别连着套。表格里的字段名不算超标。

## 七、不要写的东西

- emoji 和各种状态图标（勾、叉、火箭这种）。callout 的 emoji 属性是唯一例外，一篇最多两个。
- 首先 / 其次 / 最后 / 综上 / 总的来说 / 值得注意的是 / 不难看出
- 段末总结句、文末"未来可期""将持续迭代优化"
- 赋能、抓手、闭环、一体化、显著提升、极大地、助力、全链路打通
- 每节等长、三段排比、小标题凑成"优势 / 风险 / 建议"
- 每个列表项都是结构相同的完整句
- 引用块里放"核心洞察：……"
- 表格凑"说明 / 备注 / 建议"列
- 每段都挑一个词加粗，或者整段染色
- 为了用满块而塞进去的表格、高亮框和彩色词

## 八、交付前自检

先跑脚本，再走金字塔。

```bash
python3 scripts/ai_tells.py <文档.xml 或 .md>
```

脚本报四件事：块水位、表格纯文字格、行内代码密度、套话和 emoji。块水位只是提示，看到"段落占比高"先想内容，不一定要加块。

金字塔四问：

1. **只读每级标题**，能不能读出一篇完整论证？读不出说明标题没写判断。
2. **只看文档标题**，别人知不知道点开能拿到什么？是问句就改成交付物。
2. **每个结论往下问一句"凭什么"**，下一块是不是答案？不是就断链。
3. **每组数一数**，是不是同类、有没有重叠、有没有漏？能不能加上数量词？
4. **开头第一屏**，答案给了没有？

口吻四问：

1. 有没有一句话是"为了让结构完整"才写的？删。
2. 有没有小节其实没内容？留标题比编内容好。
3. 每个结论旁边有没有数据或出处？没有就补，或降级成"待验证"。
4. 换个同事看，会不会觉得"这人在讲解我"？会的话把解释性过渡全删掉。

最后一问：**这篇里任何一个块，删掉之后读者会变差吗？** 不会就删。

## 九、写飞书文档的执行顺序

0. 搜内部资料 → 出金字塔化的 brief → 等确认。
1. 本地写 `<doc>.xml`，`<title>` 只出现一次，不要和 `--title` 同时给。
2. `docs +create --content @<doc>.xml`；目标已存在则 `docs +update --command overwrite`。
3. 附件不能靠 `<source name="x"/>` 凭空生成——不传真实 token 会让**整篇写入失败**，正文一个字都进不去。用 `docs +media-insert --type file --file <本地> --file-view card --selection-with-ellipsis "<定位文本>"`，实测落成 `<figure view-type="Card"><source …/></figure>`。它落顶层块，**进不了表格单元格**。
4. 写完 `docs +fetch --detail full` 回读校验：颜色、callout、代码块、cite 有没有解析出标题。默认 `--detail simple` 会剥掉样式，看着像没生效，别被骗。
