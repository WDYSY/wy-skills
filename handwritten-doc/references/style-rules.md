# 风格细则与改写对照

样本：「旅游千手 - 框架层」这类内部 wiki。下面每条都带样本原句，写的时候照着感觉走，不要照着抄格式。

## 一、结构

### 中文序号只到二级

`## 一、背景` / `## 二、调研` / `## 三、功能` / `## 其他`。最后那节"其他"是杂物篓，会议纪要、归档、不再跟进的东西全塞进去，不编号。

三级以下一律 `###`、`#####`，会出现 `#####` 直接跟在 `###` 后面的跳跃，不补齐。

### 空节允许存在

样本里「### 调用统计skill」下面一个字都没有。正在搭骨架的阶段就是这样：标题先占位，内容后补。不要在没内容时编一段话凑满。

### `---` 切段

几乎每个二级小节结束都有一条 `---`。作用是视觉上一刀切开，让滚动时能看到"这节完了"。

### 标题短

`选型`、`实验对比`、`知识库相关`、`完结归档`、`暂不再跟进`。最长不过七八字，且多是名词或动宾短语。

## 二、引用块 `>` 的三类用法

1. **原料原话**：

   > 公司目前提供的知识库rag相关的主要有：compass、baymax（会合到AgentArk）、AgentArk

2. **自己下的短结论**：

   > 简单对比：
   >
   > 【速度】核心结果：

3. **旁白式的自省**：

   > 回到你最初的问题（商品后台需求 / 景玩 toC 前端需求）——我前面凭"HR 上叫'商品后台'的组"、"叫'toC 前端'的组"来给你路由，其实是用组名字面猜业务，不够可靠。

引用块里可以是长段口语，允许破折号、允许"压根""其实""不够"。但不要出现"核心洞察""一句话总结"这类标签。

也不是每个判断都值得划出来。判断写在段落第一句同样有力，一整页全是引用块，等于什么都没强调。

## 三、数字与实测口径

样本里的数字几乎都带限定词：

- `V0 BFS：约 33.7 秒，产生 51 次 HTTP 请求，仅完成 22 个 token 遍历，尚未生成答案。`
- `V2 相比 V1 的检索等待约快 150 倍。`
- `V2 出现过一次 15 秒冷启动/抖动。`
- `端到端：从 3-5min，降到1min30s左右`

写不出来的就写"准确率待测"。留白是被允许的，编一个"提升了 30%"不行。

数字后面常直接跟一句人话解释它意味着什么（"尚未生成答案"），这是人写数字的习惯，AI 只写数字。

## 四、口语与保留意见

样本里能看到写作者的态度：

- 它压根没有"业务领域"这个维度
- 同一个业务……HR 上是三条完全独立的分支，光靠这张表没法把它们串起来
- 不是我前面凭组名猜业务，不够可靠
- 准确率待测
- （共建简单参与下）
- 历史已经有一部分，确认下不要重复，desc重叠

适度吐槽是手写的标志，但吐槽对象是方案和自己，不是人。语气到"这条不稳"为止，不要阴阳。

## 五、原料直接贴

CLI 输出、检索报文、JSON 返回原样进代码块，不删字段、不重排、不加注释性前缀：

````markdown
```Plain Text
run :
.venv/bin/python .agents/skills/feishu-doc/scripts/agentark_client.py \
  --query "景玩产量宽表有哪些核心字段" --timeout 6

output:
{
  "answer": "## 景玩产量宽表核心字段\n\n…",
  "tool_calls": [ … ]
}
```
````

注意样本用了 `Plain Text` 甚至 `XML` 标一段纯文本和一段 JSON——标错语言是常态，别为了规范去改。

裸 URL 直接一行放正文：`https://agentark.release.ctripcorp.com/mcps/2878d15f-...`

## 六、表格当账本

样本的表格只有 2–3 列，一格塞一大坨：

| 日期 | 内容/待办 | 进度 |
|---|---|---|
| 2026-7-27 | 【日期规划 - 7/27 这一周跑通】会议纪要引用 + 四条 bullet，其中一条还嵌两级子列表 | |

| Scope | Details | 其他 |
|---|---|---|
| 基础信息 | Why / How 两层有序列表，How 里再嵌两层 | 截图 |

也就是说：结构靠单元格内部的列表撑，不靠拆成更多列。

## 七、AI 味对照改写

| AI 会写 | 改成 |
|---|---|
| 首先，我们需要明确知识库的定位 | 知识库先解决一件事：常见问题别再问第二遍 |
| 综上所述，AgentArk 在性能和易用性上都更具优势 | 最终采用 AgentArk。V2 直连比 V1 快很多，但只返回切片 |
| 该方案显著提升了检索效率，降低了调用成本 | 检索从 14 秒级降到 0.2 秒级，但答案要自己拼 |
| 值得注意的是，冷启动场景下仍存在抖动 | 冷启动有时候会抖，见过一次 15 秒 |
| 建议后续持续优化召回准确率 | 准确率待测 |
| 采用 XX 架构实现统一接入与能力沉淀 | 抽一层公共框架，各产线 skill 挂上去 |
| 本文档旨在梳理……，为后续……提供参考 | （直接删掉这句，从背景第一句事实开始） |
| 优势 / 风险 / 建议 三个对称小节 | 只写实际存在的两三个点，剩下的不写 |

## 八、层次与证据链

人工文档和 AI 文档最大的差别不在句子，在**深度分布**：人只在真正重要的地方往下挖，挖到能自证为止，其他地方一句话带过。AI 每节都写三段、深度一样、密度一样，看着齐整，读着空。

### 四层递进

结论 → 子结论 → 数字 → 原始材料。重要的判断要走满四层，次要的只留第一层。

```xml
<callout emoji="💡" background-color="light-yellow" border-color="yellow">
  <p>结论：HLE 榜首是国产模型，但综合榜前十一个都没有。</p>
</callout>
<p>子结论：三个综合榜的第一名都是 Gemini 4 Carbon；HLE 榜第一是 Kimi K3.1 Pro 70.00。</p>
<table>
  <thead><tr><th background-color="light-gray">榜</th><th background-color="light-gray">第一名</th><th background-color="light-gray">分</th><th background-color="light-gray">版本日期</th></tr></thead>
  <tbody><tr><td>HLE</td><td>Kimi K3.1 Pro</td><td>70.00</td><td>10-29</td></tr></tbody>
</table>
<pre lang="Plain Text" caption="原始抓取返回（2026-11-01 13:52）"><code>{"rank": 1, "model": "Kimi K3.1 Pro", "org": "Moonshot AI", "score": 70.00}</code></pre>
```

### 四个常用挂点

- 数字后面标口径：70.00（HLE 百分制，页面版本 10-29）。
- 结论后面挂 chip：<cite type="doc" doc-id="TOKEN"></cite> 或者裸 URL。
- 原始报文塞代码块，正文只留提炼后的两三行。
- 附件挂原始数据，让读者能自己复算。

### 深度不对称的写法

同一节里允许一段只有八个字，下一段是四层嵌套的表格 + 报文。看到"每段都差不多长、每节都有三个要点"，就是 AI 了。

### 存疑要单独成节

写清：哪条没验证、为什么没验证（抓不到 / 页面没给 / 权限不够）、打算怎么补。这一节最能证明是人写的——AI 倾向于把不确定的地方也说得斩钉截铁。

## 九、什么时候不该用这套

- 对外发布、需要评审签字的正式文档：要有结论段和责任人。
- 排障报告给领导看：现象和根因要写全，不能只留碎片。
- 用户明确要求"结构完整/正式一点"时，按用户说的来，这套风格只是默认值。

## 十、机械自检脚本抓不到的部分

脚本只管套话、emoji、行内代码密度、块丰富度。以下要靠自己读：

- 每个小节是不是都在"讲解我"（把读者不知道的背景耐心解释一遍）。
- 段落长度是不是过于均匀——人手写会长短不一，有的一句话独立成段。
- 是不是每节结尾都补了一句总结。
- 通篇有没有"信息量空转"的句子：正确但删掉不影响任何判断。
- 有没有哪个结论完全悬空——既没数字也没出处，那就得降级成"待验证"。
