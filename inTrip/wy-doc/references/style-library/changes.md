# 改稿台账

每改一次文档，记一对（AI 原文 → 她改成什么）。这是最准的偏好证据：不是她说喜欢什么，是她动手改了什么。

---

## 怎么回收改动（agent 执行，她不用动）

她改文档用的是飞书的 **Suggesting 模式**（工具栏显示 Suggesting）。每条改动都是一条结构化建议，带类型和时间，比 diff 精确得多。

**回收流程（首选：读建议）**

1. 浏览器打开文档（内置浏览器够用）：
   ```
   node scripts/browser.mjs open "<文档 URL>" --in builtin
   node scripts/browser.mjs screenshot --out /tmp/doc.png      # 确认右侧批注面板已展开
   node scripts/browser.mjs js "const t=[...document.querySelectorAll('div')].map(d=>d.innerText||'').filter(x=>/Suggestion/.test(x)&&x.length<8000).sort((a,b)=>a.length-b.length)[0]; return t"
   ```
   返回形如：
   ```
   Comments (15)
   Suggestion  Joann Wang (王妍)  27 min ago (edited)  Delete: "这是"
   Suggestion  Joann Wang (王妍)  27 min ago           Add: "仅"
   Suggestion  Joann Wang (王妍)  26 min ago           Format: "Strikethrough"
   ```
2. 逐条归因（四类：推演 / 元叙述 / 口语连接 / 比喻解释），写进下面的记录区。
   - `Format: "Strikethrough"` = 整段删，按段落内容归因
   - `Delete + Add` 成对出现 = 改写
   - `Add` = 她补的写法，价值最高，直接当新规则候选
3. 同一类归因攒到 3 次以上 → 往 `rules.md` 加一条，引用她的原句。

**备用流程（读不到建议面板时：回读历史版本做 diff）**

文档保留了每一次 revision，可以按版本号回读：

```bash
docs +fetch --doc <url> --doc-format markdown --revision-id <我交付时的版本> --jq .data.document.content
docs +fetch --doc <url> --doc-format markdown --jq .data.document.content
```

两次输出各存一个临时 `.md`，跑 `python3 scripts/recover_edits.py <交付版.md> <当前版.md> --title "<标题>"`，
输出一段带归因的台账表格。

**注意**：开放 API 只能按 revision 号取内容，**取不到每条 revision 的编辑人**（编辑历史只在 UI 里）。所以要靠"我交付时的 revision 号"当分界——之后的改动都算她的，别人改的也一并记入并标注。

### 改掉的写法

| AI 原文 | 她改成 |
|---|---|
| 标题「调研：vai 与 B 端流程的指令怎么对齐」 | 「调研：vai 与 B 端流程的指令对齐方案」——标题写交付物，不写问句 |
| 背景段整段铺陈"保留还是收敛"的两种可能 | 「目前需要整合二者，需要弄清当前二者的各层结构及使用方式，决定最终的融合方案。」——直接写目标 |
| 五、三条只有加粗开头 | 每条前面加短标签：「人层对齐：」「粒度对齐：」「stage单独落账：」——标签 + 冒号，便于扫读 |
| 「这是过程记录，结论未定。」 | 「这是**仅**过程记录，结论未定。」——补一个"仅"把语气收死 |

### 归纳

1. **凡是在解释"我为什么这么写""这份文档要干什么"的句子，全删。**
2. **比喻和推演一律不换，直接删，不留替代表达。**
3. **列表项前面要有标签**，这是她主动加的写法，不是删改。
4. 她保留了大量表格和代码块——**结构和证据不动，只动论述层的口水**。
