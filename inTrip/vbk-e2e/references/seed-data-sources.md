# 起点数据的两条来源：成品（造数台）与中间态（列表页/DB → 复制）

> Step 4 的决策依据。一句话：**造数台只产出「有效+上线+可订」的成品；中间态（刚建好、只点亮「销售控制」「产品信息」两个页签、未上线未置有效）拿不到，要去产品列表页（或 DB）找现成的中间态产品，打开后点「复制」，用复制出来的新产品当起点。**

## 先判定：这次要哪种起点

| PRD/用例里的信号 | 要的起点 | 走哪条 |
|---|---|---|
| 「已上线产品」「可订」「班期可售」「分销渠道可见」「预览」 | 成品（有效+上线+可订） | 造数台一键造数（原路径，[zaoshutai-guide.md](zaoshutai-guide.md)） |
| 「新建后」「刚创建」「未上线」「产品制作中」「配置流程」「还没配行程/资源/价格」 | **中间态** | 本文 B1 → B2 → B3 → B4，取一个复制出来的新产品 |
| 说不清 | 中间态 | 中间态是「从零配置」场景的天然起点；断言里已含「可订/上线」才改走造数台 |

一条需求两种都要时，按用例拆：配置类用例用中间态，展示/可订类用例用造数台成品；台账 `products[]` 每条形如 `{state, source}`。

## 中间态的定义（前端事实，2026-11-26 读码确认）

- 顶部页签由后端 `getSubMenu`（SOA 15638）下发，前端只按 `menus[].enabled == 'F'` 置灰（[SubMenu.js:961]）：**「只点亮销售控制和产品信息」= 后端只给这两个 enabled，其余 F**；
- 复制成功后前端**自动打开销售控制页** `/ivbk/vendor/saleControlMerge?from=<from>&productType=0&productId=<newProductId>`（[SubMenu.js:1075]）——即复制产物的落地页就是中间态的默认页；
- 「复制」按钮的出现条件：`meta.isBaseInfoSwitched == 'T'` 且不是子产品（`productTypeStr !== 'Child'`），6381 下还要求 `vendorId === 0`（[SubMenu.js:744]）；合同失效（`canEdit === 'C'`）不允许复制；
- 复制是**异步任务**：`POST /15638/productDuplicate.json {productId, allowAsync:true[, copyChildren]}` → 返回 `taskId` → 轮询 `/15638/getProductDuplicateResult` 到 `SUCCESS`（[SubMenu.js:1041-1110]）；父产品可选「同步复制所有子产品」；
- 复制不改产品名称/副标题，所以**必须自己把名称或副标题改成 `<releaseKey>-<序号>`**，否则没法回收对账。

## B1 产品列表页搜索 → 打开 → 复制（主路径）

1. 浏览器打开 `https://vbooking.ctrip.fat29.qa.nt.ctripcorp.com/ivbk/vendor/productListMerge?from=vbk`（与产品页同域，Step 0 那份 VBK cookie 直接够用；前端会重写到 `/product/input/productListMerge?from=vbk`，这是正常的）；
2. 用列表页筛选把候选缩小：
   - **先切到「全部」页签**（默认停在「有可售班期」，中间态产品无班期，默认页签下搜永远「暂无数据」）；
   - 「产品IDs」输入框（`data-testid="product-id-search"`，支持逗号分隔）填候选 → 「查询」；也可直接按 `baseInfoMerge?productId=<ID>&from=vbk` 打开；
   - 需要从列表里挑时，靠页签翻：`全部` / `有可售班期` / `无可售班期` / `无效` / `回收站`；
3. 候选打开后（浏览器会按产品类型重写路由）**先确认三件事**：
   - 页签只有「销售控制」「产品信息」可点，其余灰置；
   - 右上角有「复制」按钮（没有 = `isBaseInfoSwitched` 不为 T 或产品不可复制 → 换下一个候选）；
   - 产品 ID 与 DB/台账记录一致；
4. 点「复制」→ 弹确认框（实测文案：「产品复制不可修改"合同、产品类型、目的地城市、录入语言、报价单位、是否使用携程资源、是否可延住"信息，产品形态跟团游和自由行不可以交叉复制。」）→ 点「确定」（该按钮带 `data-testid="copy-popconfirm"`，是稳定的定位锚点）；
6. 等复制完成：接口 `productDuplicate.json` 先回 `taskId`，再轮询 `getProductDuplicateResult`（`DOING` → `SUCCESS`，实测约 40 秒）；**前端会用 `window.open` 开新窗口，内置浏览器/无扩展环境下可能被拦，别只等自动开窗**——用 DB 查最近 5 分钟 `CreateTime` 的新产品，或直接按候选规则验证新 ID；
7. 新产品是**草稿 ID（≥ 2e9，`Active='D'`）**，打开后通常**只有「销售控制」可点**（比源再早一档）：要拿到「销售控制 + 产品信息」两页签，先在销售控制保存一次；
8. 立刻把新产品名称/副标题改成 `<releaseKey>-<序号>` 并保存（同时验证「中间态可写」）；
9. 新产品页签再核一遍 → 写入台账 `state: "middle"`。

## 一对一派生（每用例一个副本）

**什么时候必须做**：用例里有**写操作**（保存/下一步/提交/开关），这类操作会推进后端 step，产品的中间态就没了。两个写用例共用一个产品，第二条必挂；同一条写用例的第二次执行也会挂。所以：**一场景一产品**。

派生有两种做法，**优先 A（可反复执行），A 不适用时用 B**：

### 策略 A｜链式复制（用例内先复制再执行）—— 推荐，**2026-11-26 已实测可行**

所有用例都指向**同一个模板中间态产品 P0**；每条用例的 flow 开头固定三步：

```yaml
- aiAssert: 页面状态条显示「产品：<P0>」          # 确认开的是模板
- aiTap: 点击页面右上角的「复制」按钮
- aiAssert: 弹出复制确认框，框内文案包含「产品复制不可修改」
- aiTap: 点击确认框中的「确定」按钮
- sleep: '20000'                                   # 复制是异步任务，实测 20s 够
- aiAssert: 页面已切换到复制出的新产品的销售控制页，产品ID 不再是 <P0>
- aiAssert: 新页面上「销售控制」页签可点，右上角存在「复制」按钮
...后续步骤都在副本上执行...
```

**实测结论（2026-11-26，fat29，task 1724888）**：

- ✅ 可行：用例从 P0 `2145289661` 开始 → 用例内点复制 → **WebAi 跟着 `window.open` 跳到了新产品页** `2145289656`；一键断言「产品ID 不再是 P0」通过；总时长 **68 秒**；
- ✅ 模板不被污染：执行后 P0 仍是「销售控制」可点、其余 9 个灰（只读得以保住）；
- ✅ 每次执行都会产生一个新草稿产品（DB `Active='D'`），所以**台账必须记 taskId ↔ 新产品 ID**，并配合清理；
- ⚠️ 断言必须写「产品 ID 已不是 P0」这类**可观察变化**，否则即使复制没成功也可能误判通过；
- ⚠️ 复制等待用 `sleep 20` 够用，但更稳的是 `aiWaitFor` 等「产品ID 变了」；
- 好处：P0 永远干净，用例可无限重跑；代价：每条用例多约 60 秒。

### 策略 B｜执行前批量派生（模板不可复制 / 需固定 ID 时）

1. 先定 N（用例数）和源产品（仍是两页签 + 有「复制」那个）；
2. 在源产品页**连续点击「复制」+ 确认** N 次（异步任务各自跑，不用等前一个出 ID）；
3. **用 DB 推 ID**（比等前端弹窗可靠）：
   ```sql
   -- 按创建时间窗口排 shard 0..15（逐批 UNION，一次 8 片），拿本次新增的草稿
   SELECT ProductID, Active, CreateTime FROM prd_product_0
   WHERE VendorID=<供应商ID> AND CreateTime > '<开始时间>'
   UNION ALL … ORDER BY CreateTime DESC LIMIT 20;
   ```
   特征是 `Active='D'`、ID ≥ 2e9；一次会多出几条（重复点确认会多派一个），**多出来的当备用**；
4. 每条用例只用一个副本（`config_jump_url` 里的 productId 不同），用例名带副本 ID；
5. 写用例在台账打 `destructive: true`，用例名里标「（破坏性）」；
6. 断言写「状态被推进」而不是「页面没变」：保存前断言「产品信息页签为灰置」，点击下一步后断言「产品信息页签变为可点」；
7. 重跑前先看台账：`destructive` 用例的副本已被推进 → 重新派生，不要在原副本上重试。

### 模板产品命名（硬规范）

自己造/派生的产品，名称统一写：

```
<releaseKey> · triptest验证流程产品，勿动！！！
```

例：`XLSP-5302 · triptest验证流程产品，勿动！！！-01`

- 复制**不继承名称**（派生出来 Name 为空），所以派生后第一件事就是改名；
- 源产品（别人的/既有的）一律不改名，只改自己派生的副本。

### 兜底：模板 P0 不能用了怎么办

| 现象 | 判断 | 处理 |
|---|---|---|
| P0 页签不再是最初几步（被别人保存/推进过） | 页面核页签 + 状态条 | 换本轮新派生的干净副本当模板；台账把 P0 标 `templateLost` |
| P0 打不开 / 报产品不存在 | 页面报错 | 按台账 `sourceProductId` 重新找源；再不行回 DB 检索 |
| P0 没有「复制」按钮 | 页面上按钮消失 | 是子产品/类型限制 → 换候选产品 |
| 用例内复制超时/报错 | 用例失败 | 重试一次；连续失败 → 降级用策略 B 提前派生，用例改指向副本 |
| P0 被删进回收站 | 页面 404/空 | 从回收站恢复或重新派生，并把结论回写台账 |

## 执行后清理（只删自己复制的）

- 只删**本次派生出来的副本**（`source=list/db` + `sourceProductId` 指向源产品）；源产品和别人的产品一律不动；
- 删前先列清单（哪些 ID、对应哪条用例、结果、报告链接）请人确认，并在台账 `cleanup` 段里记 `{planned[], deleted[], skipped[]}`；
- 删除入口：产品列表页勾选产品 → 删除（进回收站）→ 需要彻底删再清回收站；不允许直接写库；
- 测试失败的产品**先不删**（留作取证），确认不需要回看再删。

## B2 数据库兜底（列表页搜不到 / 不知道候选 ID）

只在「列表页搜不出、或手上没有任何 candidate」时用。**DB 只负责缩范围，页签与「复制」按钮必须在页面上确认。**

- 库表：`pkgproductdb.prd_product_0..15`，**`shard = ProductID % 16`**（没有单表 `prd_product`）；`env_type=fat`；
- 关键列：`VendorID / Active / IsOnline / IsDeleted / IsAbandoned / CreateTime / DataChange_LastTime / Name / productVersion / InputLocale`；
- 中间态候选的 DB 特征：`Active='F' AND IsOnline='F' AND IsDeleted='F' AND IsAbandoned='F'`，`CreateTime` 近；`Name` 空/很短只能当线索——**实测同字段下既可能是两页签（8911072）也可能是五页签（8913824），不能当判据**；
  - `Active='D'`：**A 步看到的复制产物就是这个取值（草稿段 ID ≥ 2e9）**；把它当**被测起点**可以，当**复制源**不行（草稿产品不能直接拿来做源）；
  - `Active='T'` 但 `IsOnline='F'` 是「已置有效未上线」，页签可能不止两个，作次选；
  - `VendorID` 必须用 **cookie 所属账号的供应商 ID**（看不到别人家的产品，也复制不了）；
- 查询姿势：先单分片取候选，避免 16 片 UNION 全扫超时（DOT 16 片全扫 ≈ 30s 会 4001）：

```sql
-- DOT，db=pkgproductdb，env_type=fat（逐片执行，可只查最近动过的几片）
SELECT ProductID, Active, IsOnline, IsDeleted, IsAbandoned, CreateTime,
       DataChange_LastTime, LEFT(Name, 40) AS Name
FROM prd_product_3
WHERE VendorID = <供应商ID>
  AND IsDeleted = 'F' AND IsAbandoned = 'F' AND IsOnline <> 'T'
ORDER BY DataChange_LastTime DESC
LIMIT 20;
```

- 拿到 ID 回到 B1 第 3 步（直接开 → 核页签 → 复制）；
- 实测（2026-11-26，fat29，VendorID 30804，shard 0）：`8911072` / `8909984` = 两页签+有复制 ✅；`8913824` / `8912256` = 五页签+无复制 ❌（DB 字段与前者一模一样）——这就是为什么 DB 只能缩范围。

## B3 造数台复制（可选，未验证）

造数台「一键造数」默认跑完整就绪链（补齐 Tab → 置有效 → 上线 → 可订），**出来的一定是成品，不是中间态**。若造数台存在「只复制、不补齐」的入口，也可以拿它当中间态来源——**当前未验证**，用到时先在页面上确认产出物确实未上线、只亮两个页签，再把结论回写本文件。

## B4 兜底：页面新建

列表页「新增产品」→ 只填销售控制 + 产品信息 → 保存。等于人手做一遍，只在 B1/B2/B3 全部不可用（无候选、无权限、列表页打不开）时用，且要在台账 `source: "create"` 标注。

## 中间态的「就绪」判定（替代 Step 5 的 有效/上线/可订）

| # | 判据 | 不过怎么办 |
|---|---|---|
| 1 | productId 是数字，页面能正常打开（不落登录页、不报产品不存在） | cookie/权限问题，回 Step 0 |
| 2 | 页签只有「销售控制」「产品信息」可点 | 换候选（这是起点不对，不是失败） |
| 3 | 有「复制」按钮（来源产品） | 换候选 |
| 4 | 复制出 `newProductId` ≠ 源 ID，且新产品页签同样只亮两个 | 重试一次；再败 → 停 |
| 5 | 新产品能保存一次（名称/副标题写 `<releaseKey>-<序号>` 成功） | 权限/只读产品，换候选 |
| 6 | （仅一对一派生）同一源产品派生的 N 个副本 `productId` 各不相同且都是草稿段 | 拿 ID 查 DB 核对 |

台账里中间态这条记 `state: "middle"`、`ready: {valid:false, online:false, bookable:false}`，并注明「预期未上线，不是失败」。

## 红线

- 中间态产品**不能写「可订 / 已上线 / 分销可见」类断言**——必挂，属于用例设计错误；
- 源产品只读：**不要在列表页/DB 找到的那个产品上保存、提交、上线、打包**；所有写入都落到复制出来的新产品；
- 复制产物必须改名成 `<releaseKey>-<序号>`，台账记 `sourceProductId → productId`，否则无法回收；
- 数据库只读（DOT 生产只读；fat 也别写库），复制源的删除/清理一律只建议不执行；
- 需要「有效/上线」前置的操作（产品体检、上线申请、打包、分销）不能放在中间态用例里；
- **写用例的副本不能共享**：同一副本只能跑一次写用例；跑完就废，重跑先重新派生；
- 清理时只能删自己派生的副本，删前必须列清单给人确认。
